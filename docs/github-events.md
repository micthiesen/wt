# GitHub webhooks

The optional events daemon uses a repository webhook to refresh the same batched GitHub query used by wt. It does not build pull request state from webhook payloads. A signed delivery is only a signal to fetch current state through the user's existing `gh` authentication.

Without `[github.events]`, wt uses its normal GitHub refresh backstop and no daemon is installed or started.

## Setup

Add an events section to the active wt configuration:

```toml
[github.events]
host = "127.0.0.1"
port = 8765
secret_file = "~/.config/wt/github-webhook-secret"
```

Then run:

```sh
wt events secret   # create a private secret file, if it does not exist
wt events install  # write this repository's per-user launchd agent
wt events start
wt events status
```

`wt events secret` does not replace an existing secret. If `secret_file` is not configured, it prints a new secret for you to add as `secret` under `[github.events]`. `install` requires a persistent secret before it writes the agent. Secret files are created with owner-only permissions.

Configure a GitHub repository webhook to send `application/json` to `https://<your-domain>/webhook`, forwarding to the configured host and port. Select `pull_request`, `pull_request_review`, `pull_request_review_thread`, `issue_comment`, `check_suite`, `check_run`, `status`, `merge_group`, and `push`. A reverse proxy or tunnel can expose the HTTPS endpoint. If another machine must reach the listener, bind to a trusted LAN address; the HMAC secret is the request authentication boundary.

The daemon accepts only the configured event types, limits the request body to 5 MiB, bounds concurrent requests and queued deliveries, and rejects requests whose `X-Hub-Signature-256` does not match the raw request body. HMAC verification uses a constant-time tag check. When its bounded queue fills, it coalesces overflow into one conservative refresh signal instead of retaining more request bodies.

## Files and freshness

The daemon writes three files under `<cache_root>/events/`:

- `github.json` contains the camelCase GitHub snapshot, covered branches, Unix-millisecond `updatedAt` (when the write finished), `fetchStartedAtMs` (when the GitHub read started), the writer's `writerSha`, `schema` (the snapshot format, `wt_events::SNAPSHOT_SCHEMA`) and `schemaWriterSha` (the build that wrote `schema`; the format counts as known only while it equals `writerSha`), `repository` (the repository and configuration it was written for; a reader for anything else ignores it), `rateLimit` (the GraphQL budget after that read: `limit`, `remaining`, `cost`, `resetAtMs`; absent when GitHub reported none; when GitHub is counting the token in more than one window, the one with the least left, with all of them in `rateWindows`), and `nextFetchAtMs` (the start of the last read of every branch plus the interval its budget asks for: the daemon starts no read of every branch before then). After a [scoped read](#scoped-reads) `fetchStartedAtMs` is still the start of the last read of every branch, `sweptAtMs` is when that read finished, and `branchReads` maps each branch read again since to the start of its own read. A pull request whose latest removal from the merge queue GitHub recorded carries `queueRemoval`: `reason` (GitHub's own word, empty when it gave none), `atMs` and `beforeCommitOid`. It stays on the pull request after a later enqueue.
- `github.touch` changes after a successful snapshot so an active TUI can notice fresh data.
- `state.json` contains daemon PID, port, build (`writerSha`), version (`writerVersion`), start/event/fetch timestamps, accepted event count, and the most recent refresh error. The PID stays in the file after the daemon exits. On macOS wt treats it as the daemon only while that process started no later than the recorded start time, so a PID reused by an unrelated process does not read as a running daemon or block `restart`, `reconcile` and `uninstall`.

`wt events status` displays the version and build recorded by the daemon itself,
which can differ from the CLI inspecting it. Older daemons that do not record a
version show `unknown`. The version is bound to `writerVersionSha`, so a rollback
that preserves unknown fields cannot report a leftover version from another build.
When stopped, these fields describe the last recorded run. While the snapshot's
budget window is still open, a `budget` line shows the GraphQL points left, the
minutes until the reset, and what the last read cost. That is the daemon's own
record. Under it, `account` is the login GitHub reports for the token that
`gh` uses in the main clone, and `budget now` lists every budget window GitHub
is counting that token against at that moment (see [GraphQL budget](#graphql-budget)).
Both come from GitHub when the command runs: one REST request for the login
and six GraphQL queries for `rateLimit` alone, which cost no points. `wt doctor`
prints the same two as `github account` and `github budget now`. Under the
`snapshot` line, `snapshot format differs; live GitHub reads will be used until
refreshed` means the file is not in this build's schema, and `snapshot from
another build; commands that print use it, the board reads GitHub itself` means
it is in this schema but another build's daemon wrote it.

These files are separate from the SQLite query cache. A successful snapshot replaces the previous snapshot atomically. A failed branch inventory or GitHub query leaves the last good snapshot in place and records the error. Cache reads are size-bounded; malformed snapshots are ignored, and malformed daemon state is reported as unreadable rather than treated as proof that no daemon exists.

Snapshots include local worktree branches, each local worktree's recorded [other branches](cli.md#one-pr-per-worktree) (the same set the TUI's GitHub read asks for, so the snapshot covers it), and configured remote worker branches. An unavailable remote inventory keeps its last known branch set and makes event relevance unknown, so a branch-scoped event is not discarded on incomplete information. Pull request, review, status, merge queue, and unscoped events refresh regardless of branch match. Plain issue comments are ignored; pull request comments are not.

The scheduler coalesces bursts for 1.5 seconds and enforces a 10-second minimum between fetch starts. The floor is measured from the prior fetch start, so a slow query consumes part of the interval. Continuous webhook traffic cannot postpone a pending fetch indefinitely. A `check_run` or `check_suite` delivery that only reports a run created or requested again, and a `status` delivery in state `pending`, wait behind a 45-second floor instead: they are most of a busy repository's deliveries and change nothing but an in-progress badge, which may therefore lag by up to 45 seconds. Completed checks and statuses, and every pull request, review, merge-queue and push delivery, keep the 10-second floor, and one of them arriving while a progress delivery waits is fetched on that floor. If the bounded request queue fills, one coalesced refresh, a read of every branch, preserves correctness. While GitHub reads fail, the floor doubles with each consecutive failure up to 5 minutes, so an outage's steady stream of CI deliveries does not turn into a retry loop that earns a secondary rate limit. A rate-limited GraphQL reply names its reset in its response headers (`x-ratelimit-reset` with nothing remaining, or `retry-after` for a secondary limit), which wt reads from the HTTPS reply (with `gh api --include` when it reads through `gh`), and the daemon waits until just past that; when the reply names no time, the floor moves straight to 5 minutes. The first successful read restores the normal floor. The read of pull requests that watches wait on outside the fleet uses the same spacing instead of asking again every minute. A failure that repeats is logged once, with the wait before the next read, and again only when the error changes or after a successful read; the logged and stored error keeps only a failed reply's `errors[]` messages, each once, capped at 500 characters. A failed refresh (worktree inventory, GitHub read or snapshot write) is retried on that floor without waiting for another delivery, so a daemon started before the network is up publishes its first snapshot on its own.

The TUI uses a cached snapshot only when it has the current build stamp, is no more than 90 seconds old, and covers every requested branch. Otherwise it performs its normal GitHub fetch. The periodic refresh remains the recovery path for missed webhook deliveries. A daemon snapshot counts as observed when its GitHub read *started*, so a read that began before one of your writes can never confirm that write; a snapshot without `fetchStartedAtMs` can be shown but never confirms a pending change. After an accepted GitHub write, wt reads the written pull request's branch and the merge queue directly: one batched request for the branches written since the last read, plus the usual review-thread follow-ups. It merges the answer into the shown data and stamps only that branch, its rows and the merge queue as newer. It reads every branch instead when the shown data does not cover the current branch set or the written branch. A daemon snapshot whose read of that branch began before the branch read does not replace the branch's answer or the merge queue. While one of its writes is unconfirmed, wt repeats the branch read every 5 seconds, within the rate floor. A daemon snapshot whose read started before the latest direct read of every branch never replaces it: when the branch set changed, only the new branches' entries come from the snapshot, and the combined data is stamped with the snapshot's older start. An accepted GitHub change normally waits 30 seconds for a read to show it; while no read that started after the write has finished (the rate floor deferred it, or it is slow), it waits up to 120 seconds.

## Scoped reads

A `check_run`, `check_suite` or `status` delivery changes only the checks of the branches it names, so the daemon reads just those branches (one request, 1 point, or 2 when a named pull request has unresolved review threads to attribute) and merges the answer into its last read of every branch. A branch the scoped read found no pull request for loses its entry; no other branch is touched. Every read returns the repository's merge queue, so the snapshot always carries the newest one.

Every other delivery reads every branch, as before: a pull request, review, push or merge queue delivery can move other pull requests, and those deliveries are also what follows this host's own writes. A scoped read is taken only when all of this holds, and otherwise the read covers every branch:

- every delivery waiting on the read is a check or status delivery whose branches are known worktree branches, at most 8 of them (one request);
- the daemon's last read of every branch covered exactly the branches it would ask about now, and started less than 45 seconds ago, so a reader's 90-second rule never ages out between two reads of every branch while deliveries keep arriving;
- the previous read did not fail. A failed scoped read merges and writes nothing, and the retry reads every branch.

A scoped write does not make the snapshot newer than its oldest part. `fetchStartedAtMs`, the stamp that decides whether a read can confirm one of your writes, stays at the start of the last read of every branch, so nothing is confirmed earlier than before. A reader ages the snapshot from `sweptAtMs`, not from the write. In the TUI, a snapshot whose read of every branch started before the latest direct read still never replaces that read, with one addition: a branch in `branchReads` whose scoped read started after the direct read takes the daemon's newer answer, and the result keeps the direct read's stamp. `wt wait`, `wt fleet` and the other snapshot readers see a scoped answer as soon as it is written.

With 48 branches a read of every branch is 6 requests plus the author read, 7 points; while check deliveries flow at the 10-second floor that was about 31 points every 45 seconds, and is now one such read and up to four scoped ones, about 11.

## GraphQL budget

GitHub charges GraphQL reads in points (5,000 an hour for a user token, shared with every other client of that token) at one point per hundred requests, counting one request per connection per parent node. The batched query asks, for each branch, the two newest pull requests with their review requests, last commit and its check contexts, review threads, comments, reviews and latest merge-queue removal: 15 requests a branch, so a chunk of 8 branches (121 requests with the merge queue) costs 1 point and 37 branches cost 5. It does not ask who opened each review thread, because one nested connection per thread (50 threads on each of 2 pull requests) was 100 of the former 113 requests a branch, 9 points a chunk and 42 for those 37 branches. When a selected pull request has unresolved threads, one follow-up query reads their first comment's author by thread ID, up to 100 threads a point, and only for those threads. A follow-up that fails, or omits a thread, fails the whole read like a missing chunk does. A thread that comes back `null` (deleted between the two requests, or unreadable) is different: the follow-up is retried like any transient chunk failure, and if the last attempt still has no thread, the read succeeds with that one thread's author unknown, so it counts as unresolved but as neither a person's nor the review bot's.

The batched query reads the first 50 review threads of a pull request and asks whether more follow. Only for a selected, open pull request that says so, a follow-up query reads the rest by cursor, 100 threads a page and up to 20 such pull requests a request, before the author read, so later threads are counted and attributed like the first 50. It stops at 300 threads a pull request. While threads are left unread (past that cap, or after a page that could not be read), a review bot that has finished with no finding among the threads read is shown as pending, not clean: a pull request with more than 300 review threads never reads as review-bot clean, so `wt wait reviewed` does not fire for it, and its row is marked as needing attention. This follow-up refines an answer the batched query already gave, so unlike a chunk or the author read it does not fail the whole read: when a page cannot be read (after the usual transient retries) or the pull request has more than 300 threads, the read succeeds and that pull request's thread counts are lower bounds, marked `unresolvedThreadsMore` in the snapshot and `unresolved_threads_more` in `wt fleet --json`. A rate limit or a cancellation still fails the read, so pacing sees it. The pages' cost is added to the read's cost like every other request.

Every such query also asks `rateLimit { cost remaining resetAt limit }`, and the read reports the points it spent over all its requests with what is left.

Reads go over one in-process HTTPS client, authenticated with the token `gh auth token` prints for the repository's host (asked again after 5 minutes). The chunks and follow-ups of one read run in parallel, up to 8 requests at once. wt reads through `gh` instead, 4 chunks at once, when it has no usable token or API host, and when the API cannot be reached over HTTPS before it has ever answered; it then stays on `gh` for 5 minutes and logs `GitHub API unreachable over HTTPS; reading through gh`. Writes always go through `gh`.

GitHub counts one token's GraphQL requests against more than one window at a time. Each has its own `resetAt` and its own count, each reply reports only the window that counted it, and requests are not spread evenly: in one measurement three quarters of the replies and five sixths of the points belonged to one window, while `gh api rate_limit` only ever showed the other. The window with the least left is the one that refuses requests first, so that is the reading wt keeps: a read reports the lowest `remaining` among the open windows its requests saw, and the daemon and the TUI remember each window's lowest reading until it resets, so a later read that happens to see only the roomier window does not hide the other. A window's count only falls until its reset, so a remembered reading is an upper bound.

wt uses the budget three ways:

- **Pacing.** After a successful read, the minimum interval before the next background read becomes the larger of its normal floor and `cost × time to reset × 2 ÷ spendable`, where spendable is what remains above a reserve of a quarter of the limit. The reserve is for agents working through the same token; the factor of 2 is because wt learns what they spent only at its next read. A full budget leaves the 10-second floor alone; as an hour gets busy the interval grows instead of the budget running out. The interval never exceeds the time to the reset or 15 minutes, whichever is sooner, so with only the reserve left background reads continue at one per 15 minutes instead of stopping until the reset. The interval is still measured from the prior fetch start. A reply without `rateLimit` (rate limiting switched off on GitHub Enterprise), a window already reset, or a reset more than 65 minutes away leaves the floor unchanged.
- **Who is paced.** The events daemon, the TUI's own background reads (its backstop, and reads after the daemon's snapshot ages out), and the read `wt wait` processes share. A read the user caused is not: the one after an accepted GitHub write and a hard refresh (`Ctrl+R`) ignore the budget's interval and may start up to 10 seconds ahead of the sustained rate of one read per 10 seconds, which the reads after it give back, so at most two reads start close together. `wt doctor` and merge arming always read live. Removal reads live where a command plans it: `wt rm`, `wt clean` and the cleanup automations make their own GitHub read. In the TUI the cleanup menu is built from board data, and confirming a removal does not read pull request state again: the host plans with its confirmed GitHub data, which can be an events-daemon snapshot of any age, and a merged pull request counts only for the exact HEAD it merged, or for a HEAD that holds only copies of that head, which never un-merges. What the commit does read live is everything else: the base tip origin advertises, the checkout's hazards and removal revision (rechecked under the removal lock), and one GitHub read for the worktree's [other branches](cli.md#one-pr-per-worktree) whose recorded answer is open, unknown or over ten minutes old. When such a read in the TUI is refused for the rate limit, its background reads wait for the reset the reply names, or 5 minutes when it names none. A refusal that names its reset holds the reads the user caused too, until just past the reset, or for 5 minutes when the reset is more than 65 minutes away; a successful read ends the hold.
- **Visibility.** The TUI header shows `gh 12% left (23m)` in the warning color once less than a quarter of the budget is left, and nothing otherwise. Each read logs one `GitHub fetch` line at `info` with `branches`, `requests`, `cost`, `remaining`, `limit`, `elapsed_ms`, `transport` (`https` or `gh`), `role` (the subcommand of the process that read: `events` for the daemon, `tui` for the board, `wait`, `doctor` and so on) and `pid`, so the app log can be counted to see what spent the budget and who. The TUI also logs `slow GitHub read` with `started_at` (UTC) for a direct read that took 15 seconds or more; an ordinary read of a few dozen branches takes six to ten.

`wt fleet`, `wt ls` and the landing that `wt owed`, `wt status` and the listings print only display pull request state, so they use the daemon's snapshot when it is in this build's snapshot schema (whichever release build wrote it; a development build on either side requires the same build), names the same repository, is no more than 90 seconds old and covers every asked branch. Unlike the TUI, they also use it when it is older but the budget is holding the next read back. That is the case until 30 seconds past `nextFetchAtMs` (`GitHub reads are paced, using data N min old`), and after that while the snapshot's budget is down to the reserve in a window that has not reset (`GitHub budget low, using data N min old`). Otherwise they read GitHub. `wt fleet` prints that line, or the snapshot's age in seconds, under the table and carries `pr_snapshot_age_seconds` on each live row of `--json` (`null` for a live read; a row whose branch a newer shared `wt wait` read covers carries that read's age); `wt ls` prints the line on stderr; the landing readers print nothing extra. A held snapshot is shown and never recorded: `wt fleet` does not write other-branch answers from it, and `wt done` and `wt status verified`, which close or refuse by the landing, keep the 90-second rule. `wt wait` takes a paced snapshot the way it takes its own paced answer: past 90 seconds it proves only merges, and the rest reads `unknown` until the time in `nextFetchAtMs`.

## Native launchd service

The launch agent is `~/Library/LaunchAgents/com.wt.events.plist`. It invokes the stable native launcher at `~/.local/share/wt/bin/wt` (or the configured `WT_INSTALL_ROOT`), not a source checkout, Bun, or a version-specific release directory. The plist freezes absolute global and repository config selectors, the current `PATH` used to find `git` and `gh`, and logs under `<cache_root>/events/`.

There is one `com.wt.events` agent per user. `start`, `stop`, `restart`, and `uninstall` require the plist's config selectors and log paths to prove that it belongs to the active repository. The selectors are compared as resolved: the plist records the loaded repository config's path, and an empty `WT_REPO_CONFIG` (the daemon discovers its config itself) matches whenever the global config and the events log paths do, since those paths are keyed by repository identity. Comparing the raw variable made every wt-launched session, which pins the selector, treat a shell-installed agent as foreign. Unknown ownership fails closed. `install` also refuses to overwrite a foreign or unidentifiable plist. These mutations share a per-user lock.

When wt starts with events enabled, it checks an existing owned agent in the background. "Current build" means the installed build recorded in the install state, not the build of the process doing the check, so a session that has just updated, or a development binary, does not restart the daemon repeatedly. A live process on the installed build is left alone. A stopped process or a different build is unloaded, rewritten to use the current stable launcher and absolute config selectors, and reloaded. A foreign agent is left untouched. `wt events restart` reloads the agent and waits for a new live process on the installed build. `wt events reconcile` performs the startup check on demand: it reloads this configuration's agent only when its daemon runs a build other than the installed one. It prints nothing when the daemon is current or no agent is installed, a note when the agent belongs to another configuration, and `restarted GitHub events daemon on build X` after a reload.

After `wt update` or the TUI startup update offer installs a build on macOS, and only when `~/Library/LaunchAgents/com.wt.events.plist` exists, wt runs the new launcher's `wt events reconcile` with a 90-second timeout. A failure only warns and suggests `wt events restart`; the update stays installed. On Unix the launcher replaces itself with the selected build (`exec`), so launchd's SIGTERM on unload reaches the daemon directly; its graceful shutdown is bounded to 5 seconds. The reload that follows an unload ignores cancellation, and runs even when the unload could not be confirmed, because `launchctl unload -w` also disables the job.

Launchd management is available on macOS. `wt events serve` can also run in the foreground on other platforms for diagnostics or deployment under another service manager. It exits on SIGTERM/SIGINT and does not install a service there.

The daemon starts an origin fetch beside a GitHub query, one at a time, only when something since the last fetch could have moved origin's refs: its first refresh, a `push` or `merge_group` delivery, a `pull_request` delivery other than label, assignment, review-request, draft, lock, milestone, auto-merge or merge-queue changes, and a coalesced queue overflow. Check, status, review and comment deliveries refresh GitHub without fetching origin. The GitHub query and the snapshot do not wait for the fetch. A ref-changing delivery that arrives during a fetch gets its own fetch when that one ends; after a failed fetch the request is kept and retried at the next refresh. The log records each origin fetch once at `info` (trigger `events daemon`) with how long it took, including any wait for a fetch already in progress; the delivery that prompted it is logged at `debug`. A failed `git fetch origin --prune` is logged and does not prevent the GitHub refresh. Updating safe local base/`keep_fresh` refs remains owned by the shared repository freshness service and is not part of this daemon's refresh operation.
